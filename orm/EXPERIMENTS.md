# 가설 기록

이 폴더는 완성된 ORM 제품보다 **반증 가능한 실험**을 우선합니다. 한 번에 바꾸는 요인과 반환값 계약을 명시하고, 빠른 결과만 선택해 기록하지 않습니다.

## H001 — 같은 최종 JS 객체를 만들 때 C 매핑이 더 빠른가?

- 가설: JS에서 네이티브로 한 번 호출하여 필터링·디코딩·객체 생성을 수행하면, 준비 시 생성한 JS 매퍼보다 wall time과 CPU time을 줄일 수 있다.
- 비교: 같은 Buffer와 모델/조건/projection/limit을 사용하는 `generic`, `compiled`, `native`.
- 비용 범위: 헤더와 접근 셀 검증, 필터링, 문자열 디코딩, 최종 JS 배열·객체 생성. 픽스처 인코딩과 쿼리 준비는 제외한다.
- 정확성: 원본 데이터에 대한 별도 oracle, 숫자 경계, null, Unicode/NUL, 조건 AND, projection 순서, limit, 손상 버퍼 검사를 통과해야 한다.
- 판정: 시나리오별 수치를 보존한다. 생성 JS 대비 C의 일관된 개선이 없으면 'C로 옮기면 빨라진다'는 가설을 채택하지 않는다. 단일 장비 한 번의 측정으로 일반화하지 않는다.
- 초기 결과: 이 장비에서는 **지지되지 않음**. 전체 조회의 median은 생성 JS 3.531ms, C 5.547ms였고, 필터/limit 시나리오에서도 C가 더 느렸다.
- 해석: 현 구현의 경계 호출, Node-API 속성 설정, 문자열 처리 등을 합한 결과다. 각각의 비용 비중은 별도 프로파일 없이 단정하지 않는다.

## H002 — SQLite에서 중간 JS 행을 없애면 이득이 있는가?

- 가설: SQLite C API에서 최종 ORM 객체를 직접 만들면 `node:sqlite` 결과를 다시 매핑하는 경로보다 빠르다.
- 비교: 동일 모델 데이터, 동일 SQL·바인딩·projection·limit. Node 기본 driver 반환도 대조군으로 기록한다.
- 비용 범위: 준비된 statement 실행부터 최종 객체 반환까지. 파일 생성/삽입/준비는 제외하며 warm-cache 읽기다.
- 정확성: 세 ORM 경로는 같은 값과 JS 타입을 반환해야 한다. raw 대조군은 동일한 스칼라를 갖는 projection에 한정하고 prototype 차이를 기록한다.
- 초기 결과: **일관된 이득 없음**. 전체 조회 median은 driver 3.735ms, 범용 JS 5.061ms, 생성 JS 6.154ms, C 6.036ms였다. 작은 limit 조회에서는 C가 생성 JS보다 빨랐지만 driver/범용 JS보다 느렸다.
- 교란 요인: 이 장비는 Node SQLite 3.53.4, 시스템 SQLite 3.54.0이다. H002는 구현 경로 전체의 비교이며 언어 또는 매핑만의 인과 효과로 해석하지 않는다.

## 후속 후보 — 아직 검증하지 않음

1. **동일 SQLite 빌드 비교:** 라이브러리 버전과 빌드 옵션을 맞춘 대조군으로 H002의 교란 요인을 줄인다.
2. **관계 조립:** 일대다 JOIN의 중복 행을 동일한 알고리즘으로 묶는 비용을 JS/C에서 비교한다. native 구현에만 더 좋은 알고리즘을 쓰지 않는다.
3. **비동기 실행:** SQLite 실행/네이티브 처리와 V8 객체 생성을 분리하고 이벤트 루프 지연, 복사 비용, 전체 CPU를 함께 측정한다. V8 객체 생성은 해당 JS 실행 스레드에서 해야 한다.
4. **응답 전용 결과:** JS에서 결과를 가공하지 않는 요청에 한해 네이티브 결과 핸들 → 직렬화와 전체 JS 객체 반환을 비교한다. 일반 ORM 객체와 다른 계약임을 명시한다.
5. **실제 라이브러리 비교:** 동등한 SQL/관계/변환 규칙으로 TypeORM과 `class-transformer`를 추가한다. 현재 `generic`을 TypeORM 그 자체라고 취급하지 않는다.

새 실험에는 가설, 변경 요인, 기준 구현, 정확성 검사, 재현 명령, 원시 결과, 환경 정보, 해석 한계를 함께 추가한다.
