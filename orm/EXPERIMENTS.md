# 가설 기록

이 폴더는 완성된 ORM 제품보다 **반증 가능한 실험**을 우선합니다. 한 번에 바꾸는 요인과 반환값 계약을 명시하고, 빠른 결과만 선택해 기록하지 않습니다.

## H001 — 같은 최종 JS 객체를 만들 때 C 매핑이 더 빠른가?

- 가설: JS에서 네이티브로 한 번 호출하여 필터링·디코딩·객체 생성을 수행하면, 준비 시 생성한 JS 매퍼보다 wall time과 CPU time을 줄일 수 있다.
- 비교: 같은 Buffer와 모델/조건/projection/limit을 사용하는 `generic`, `compiled`, `native`.
- 비용 범위: 헤더와 접근 셀 검증, 필터링, 문자열 디코딩, 최종 JS 배열·객체 생성. 픽스처 인코딩과 쿼리 준비는 제외한다.
- 정확성: 원본 데이터에 대한 별도 oracle, 숫자 경계, null, Unicode/NUL, 조건 AND, projection 순서, limit, 손상 버퍼 검사를 통과해야 한다.
- 판정: 시나리오별 수치를 보존한다. 생성 JS 대비 C의 일관된 개선이 없으면 'C로 옮기면 빨라진다'는 가설을 채택하지 않는다. 단일 장비 한 번의 측정으로 일반화하지 않는다.
- 초기 결과: 이 장비에서는 **지지되지 않음**. 전체 조회의 median은 생성 JS 3.531ms, C 5.547ms였고, 필터/limit 시나리오에서도 C가 더 느렸다.
- 해석: 현 구현의 경계 호출, Node-API 속성 설정, 문자열 처리 등을 합한 결과다. 각각의 비용 비중은 별도 프로파일 없이 단정하지 않는다.

## H002 — SQLite에서 중간 JS 행을 없애면 이득이 있는가?

- 가설: SQLite C API에서 최종 ORM 객체를 직접 만들면 `node:sqlite` 결과를 다시 매핑하는 경로보다 빠르다.
- 비교: 동일 모델 데이터, 동일 SQL·바인딩·projection·limit. Node 기본 driver 반환도 대조군으로 기록한다.
- 비용 범위: 준비된 statement 실행부터 최종 객체 반환까지. 파일 생성/삽입/준비는 제외하며 warm-cache 읽기다.
- 정확성: 세 ORM 경로는 같은 값과 JS 타입을 반환해야 한다. raw 대조군은 동일한 스칼라를 갖는 projection에 한정하고 prototype 차이를 기록한다.
- 초기 결과: **일관된 이득 없음**. 전체 조회 median은 driver 3.735ms, 범용 JS 5.061ms, 생성 JS 6.154ms, C 6.036ms였다. 작은 limit 조회에서는 C가 생성 JS보다 빨랐지만 driver/범용 JS보다 느렸다.
- 교란 요인: 이 장비는 Node SQLite 3.53.4, 시스템 SQLite 3.54.0이다. H002는 구현 경로 전체의 비교이며 언어 또는 매핑만의 인과 효과로 해석하지 않는다.

## H003 — 복잡한 JOIN/집계에서도 C 경로의 이득이 있는가?

- 가설: 4중 LEFT JOIN과 행 증가, 관계 조립, 부모 기준 페이지네이션, 집계가 포함되어도 C 조회 경로가 생성 JS보다 일관되게 빠르다.
- 비교: 5개 테이블, 동일 SQL/바인딩/인덱스, 동일 JS 관계 조립 함수, 동일 최종 객체. 평면 행 반환도 따로 기록한다. C 관계 조립 알고리즘과 JS의 비교는 아니다.
- 정확성: 독립 엔티티 기준 oracle로 flat 행과 중첩 그래프 검증. 빈 관계, 항목 × 결제 중복 제거, 부모 페이지네이션, 합계 중복 계산 방지를 검사한다.
- 초기 결과: **일관된 개선 근거 없음**. JOIN+관계 조립은 6,739개 행 → 고객 858명의 그래프를 반환하며 median 생성 JS 10.508ms, C 10.799ms. 50명 페이지는 0.611ms 대 0.612ms, 집계는 1.609ms 대 1.708ms였다.
- 한계: SQLite 버전/빌드가 다르고 바인딩 재사용 방식도 다르다. warm-cache 단일 장비의 첫 측정이며 근소한 차이에 통계적 유의성을 주장하지 않는다. JOIN/집계의 EXPLAIN QUERY PLAN과 원시 수치를 보존한다.

## H004 — 트랜잭션의 원자성을 유지하며 C 경로가 비용을 줄이는가?

- 가설: 동일 연결에서 debit/credit/원장 INSERT/잔액 SELECT/COMMIT을 수행할 때 C 세션이 생성 JS보다 비용을 줄인다.
- 구현 조건: 기존 `openSqlite()`의 Node/C 별도 연결을 섞지 않고, `openSession()`이 실행기별 단일 연결을 소유한다. `BEGIN IMMEDIATE`, WAL, synchronous=FULL, FK/CHECK와 자동 체크포인트 조건을 맞춘다.
- 정확성: 미커밋 쓰기 읽기, 커밋 결과, 의도적 롤백, 중간 FK 실패 롤백, 연결 종료, 중첩/비동기 콜백 거부를 검사한다. 벤치마크 종료 후 성공 횟수에 맞는 잔액·원장 개수도 검사한다.
- 초기 결과: 커밋 median 생성 JS 0.037ms, C 0.051ms. 롤백은 각각 0.006ms, 0.008ms. **이 설정에서 개선은 관측되지 않았다.** 내구성 설정은 같지만 OS/SQLite 빌드 차이와 파일시스템 비용을 포함하므로 C 언어 자체의 효과로 해석하지 않는다.

## H005 — C 동기 호출로 옮기면 락 경합과 이벤트 루프 지연이 줄어드는가?

- 가설: 같은 DB에서 writer가 경쟁할 때 C 동기 호출 경로가 락 대기를 이벤트 루프에서 분리하거나 처리량을 크게 개선한다.
- 비교: 실제 worker 연결이 writer lock을 잡은 뒤 메인 스레드가 다른 행에 쓰기를 시도한다. timeout 실패와 해제 후 성공을 분리하고 `setImmediate` 지연을 측정한다. 별도로 3개 worker가 각 40개 송금을 반복한다.
- 정확성: WAL reader는 이전 커밋 값을 읽고, 오래된 snapshot의 쓰기 전환은 SQLITE_BUSY로 실패한다. timeout 후 복구와 모든 최종 잔액·원장 일치를 검증한다.
- 초기 결과: **동기 C 호출도 이벤트 루프를 막았다.** 60ms 락 보유 시 C 호출 median 65.684ms 동안 setImmediate도 65.736ms 지연되었다. 이 세 호출의 프로세스 CPU는 각각 0.870/1.180/0.876ms로, wall time 증가가 같은 크기의 CPU 계산을 뜻하지 않았다.
- 경합 결과: 트랜잭션 내 의도적 2ms 락 보유에서 생성 JS 373.6 tx/s, C 373.7 tx/s. 작업 p99는 각각 108.031ms, 112.077ms. 네이티브로 이동하는 것만으로 writer 직렬화가 사라지지는 않았다.
- 한계: 의도적 보유 시간이 처리량을 지배한다. closed-loop 부하이며 지연에는 재시도/backoff가 포함된다. HTTP/GraphQL 지연, PostgreSQL/MySQL의 행 락, 비동기 ORM 구현을 검증한 결과는 아니다.

설계 및 재현: [복합 실험](COMPLEX.md). 결과: [보고서](results/2026-10-01-complex.md), [원시 샘플·SQL·실행 계획](results/2026-10-01-complex.json).

## 후속 후보 — 아직 검증하지 않음

1. **동일 SQLite 빌드 비교:** 라이브러리 버전과 빌드 옵션을 맞춘 대조군으로 H002의 교란 요인을 줄인다.
2. **C 관계 조립:** H003의 관계 조립은 모든 경로가 같은 JS 함수다. 후속 실험에서는 일대다 JOIN의 중복 행을 동일한 알고리즘으로 묶는 부분 자체를 JS/C에서 비교한다. native 구현에만 더 좋은 알고리즘을 쓰지 않는다.
3. **비동기 실행:** SQLite 실행/네이티브 처리와 V8 객체 생성을 분리하고 이벤트 루프 지연, 복사 비용, 전체 CPU를 함께 측정한다. V8 객체 생성은 해당 JS 실행 스레드에서 해야 한다.
4. **응답 전용 결과:** JS에서 결과를 가공하지 않는 요청에 한해 네이티브 결과 핸들 → 직렬화와 전체 JS 객체 반환을 비교한다. 일반 ORM 객체와 다른 계약임을 명시한다.
5. **실제 라이브러리 비교:** 동등한 SQL/관계/변환 규칙으로 TypeORM과 `class-transformer`를 추가한다. 현재 `generic`을 TypeORM 그 자체라고 취급하지 않는다.

새 실험에는 가설, 변경 요인, 기준 구현, 정확성 검사, 재현 명령, 원시 결과, 환경 정보, 해석 한계를 함께 추가한다.
